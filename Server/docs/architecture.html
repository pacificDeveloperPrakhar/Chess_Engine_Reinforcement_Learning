Chess Server Design

WebTransport over QUIC · one "interface" thread · 10 worker tasks · 100 connections · waiting line

This is a reference for the game server in Server/, written to match the code as it is now. It covers four things: how the server is structured, how a client gets in, how a request is handled, and how the server is tested and measured. Every component shown exists in the code; nothing is planned or assumed.

1. Threads and the interface

The main thread starts one thread, named interface, and waits for it to finish. The interface thread runs a tokio current-thread runtime inside a LocalSet. On it run exactly 11 tasks: the interface, which accepts and admits clients, and 10 worker tasks, which handle all 100 connections between them.

Single thread, but asynchronous

QuestionAnswer
How many threads do the work?One: interface. main only waits.
How many tasks?11: the interface plus 10 workers, fixed at startup. (wtransport's QUIC library also runs its own internal tasks on this thread.)
How does one worker serve 10 connections?It keeps one pending future per connection ("next stream") and one per stream ("write the last reply, then read the next frame") in a FuturesUnordered, and handles whichever becomes ready.
Are clients served in parallel?No. Only one piece of code runs at any instant.
Are clients served concurrently?Yes. All 100 connections are in progress at once; the 10 workers and the interface take turns on the thread.
When does a task give up the thread?When none of its futures is ready. Because writes happen inside each stream's own future, a slow client only holds up its own stream, not the rest of its worker.
Why no locks?handle_request has no .await, so one request finishes before the next one starts, and only this thread touches the store.
What would freeze everyone?Slow synchronous work inside handle_request, such as a deep engine search. That kind of work belongs on spawn_blocking.
Every slot stores a unique client id, and lookups check the slot index and the id together. A stream left over from a client that has gone can therefore never change the next client that takes the same slot.

2. How a client gets in

Admission is a tokio::sync::Semaphore with one permit per slot. Its wait list is the buffer that holds clients until a slot is free. A session holds its permit until the client leaves, so holding a permit guarantees a free slot.

SituationWhat happens
A slot is free and nobody is waitingThe client enters immediately
All 100 slots taken, fewer than 50 waitingThe client waits in line
A connected client leavesIts permit goes straight to the client that has waited longest
50 already waitingRefused at once with 429 (LineFull)
Waited 30 s with no free slotRefused with 429 (TimedOut)
Ctrl-CEvery waiting client is refused (Closed), and every connection is closed

The limits are constants: MAX_CONNECTIONS = 100 in src/connections.rs, and MAX_WAITING = 50 and MAX_WAIT = 30 s in src/admission.rs.

3. How a request is handled

RequestPayload lengthServer reply
GetFen1Fen of this client's board (32 bytes)
SetFen32Stores the board in the slot, replies Fen of it
Select(u64)8Select with the same square (an echo until the engine is connected)
Move17Move unchanged (an echo until the engine is connected)
any other length—Zero-length error frame; the stream stays open

Wire frame

[ len: u8 ][ payload: len bytes ]      same in both directions

len  1 → GetFen         (request)
len  8 → Select(u64)    (request and response), big-endian
len 17 → Move           from u64 + to u64 + role u8, big-endian
len 32 → SetFen / Fen   64 squares × 4 bits (piece << 1 | colour)
len  0 → error frame    (response only)

4. How performance is tested

examples/smoke_client.rs is a real WebTransport client. It includes the server's own src/Payload code through #[path]. Its request dispatcher therefore builds requests with Request::encode and reads replies with Response::decode, the exact inverse of what the server does.

Results (localhost, release build, 3 runs, all passed)

MeasurementResult (range over 3 runs)
Burst: 100 Moves at the same instant, all replies3.4 – 5.8 ms (round trip p50 1.8 – 3.5 ms)

How to run it

# terminal 1: the server prints "cert sha-256: …"
cargo run --release
# terminal 2: pass that hash to the test
cargo run --release --example smoke_client -- <cert-sha256>
What the test does not cover: a real network (everything runs on one machine, so there is no real latency or packet loss), a real browser client, the 30 s wait timeout, and real chess rules (Select and Move are echoes until the engine is connected).
